# ИИ-агент поиска ответов по корпоративным документам (RAG)

Агент отвечает на вопросы сотрудников по внутренним документам компании
(регламенты, приказы, инструкции, договоры): кто подписывает договор,
какой регламент действует, кто отвечает за этап. Информация ищется
семантически — по смыслу, а не по ключевым словам, с указанием источника.

Стек: **Java 21 · Spring Boot 3.5 · Spring AI 1.1 · PostgreSQL 17 + pgvector · OpenAI-совместимый API** (эмбеддинги `bge-m3-rus1`, генерация `deepseek/deepseek-v4-flash-0731`).

## Архитектура

Два контура (по схеме Spring AI RAG):

```
Офлайн (ETL)   файл → TikaDocumentReader → TokenTextSplitter → EmbeddingModel (bge-m3-rus1)
               → PgVectorStore → PostgreSQL (vector_store, HNSW-индекс) + каталог documents

Рантайм (RAG)  вопрос → EmbeddingModel → поиск top-5 в pgvector (косинусная близость)
               → промпт «контекст + инструкция + вопрос» → deepseek-v4-flash → ответ + источники
```

Ключевое правило агента (анти-галлюцинация): **отвечать только по регламентам;
если ответа в них нет — не отвечать наугад, а создать заявку в службу качества.**
Правило обеспечено не только промптом:

- модель возвращает не текст, а структуру `found / answer / quotes`;
- ответ показывается пользователю, только если каждая цитата дословно найдена
  в найденных фрагментах регламента и все числа ответа взяты из них же
  (`QuoteVerifier`); не прошло проверку — одна повторная попытка, затем заявка;
- вместе с ответом пользователь видит дословные цитаты из регламента.

## Подготовка окружения

Есть вариант без локальной установки PostgreSQL и JDK — раздел «Запуск в Docker»
ниже: приложение и база с pgvector поднимаются через `docker compose`.
Дальше описана локальная установка.

1. **PostgreSQL 17** с расширением **pgvector** — поднят как **отдельный
   инстанс** (служба Windows `pg-rag`, автозапуск), чтобы не зависеть от
   основного сервера на 5432:

   | Параметр | Значение |
   |---|---|
   | Каталог данных | `C:\Users\kysik\pg-rag` |
   | Порт | `5433` |
   | Логин / пароль | `postgres` / `postgres` (локальный демо-инстанс) |
   | БД | `rag_docs` с расширением `vector` 0.8.7 |

   Управление службой: `net start pg-rag` / `net stop pg-rag`,
   или через services.msc.

2. **Токен OpenAI-совместимого API** — адрес `https://plusvibeapi.ru/v1`.
   Задаётся переменной окружения `AI_API_KEY` или строкой `AI_API_KEY=...`
   в файле `.env` в каталоге проекта (без кавычек; в git файл не попадает).
   Без токена приложение не стартует. Если провайдер выдаёт для эмбеддингов
   отдельный ключ — задайте `AI_EMBEDDING_API_KEY`; пока он пуст, используется
   общий. Модели прописаны в `application.yml`: чат
   `deepseek/deepseek-v4-flash-0731`, эмбеддинги `bge-m3-rus1`.

3. Пароль postgres: переменная окружения `DB_PASSWORD`
   (или правка `application.yml`).

4. **Логины и пароли входа**: API и страницы закрыты HTTP Basic. Учётные записи две:

   | Роль | Логин | Пароль | Что доступно |
   |---|---|---|---|
   | Пользователь | `APP_AUTH_USERNAME` (по умолчанию `employee`) | `APP_AUTH_PASSWORD` | чат с агентом |
   | Служба качества | `APP_QUALITY_USERNAME` (по умолчанию `quality`) | `APP_QUALITY_PASSWORD` | заявки и чат |

   Значения — переменные окружения или строки `ИМЯ=...` в `.env`. Без любого
   из паролей приложение не стартует. Необязательный `QUALITY_SERVICE_CONTACT` —
   контакт службы качества, который агент называет в ответе «обратитесь …».

## Запуск

```bat
cd rag-agent
mvnw.cmd spring-boot:run        (Linux/macOS: ./mvnw spring-boot:run)
```

Демо-интерфейс: http://localhost:8090/
Страница заявок (роль службы качества): http://localhost:8090/quality.html

## Аутентификация

Все запросы — и API, и страницы — закрыты HTTP Basic (realm `rag-agent`).
При открытии http://localhost:8090/ браузер сам показывает диалог входа;
после него учётные данные прикладываются к запросам автоматически.

- Учётные записи: пользователь (`APP_AUTH_USERNAME` / `APP_AUTH_PASSWORD`, роль USER)
  и служба качества (`APP_QUALITY_USERNAME` / `APP_QUALITY_PASSWORD`, роль QUALITY) —
  см. «Подготовка окружения».
- Роль QUALITY даёт доступ к странице заявок `/quality.html` и API `/api/quality-requests/**`.
  Обычному пользователю они закрыты: страница возвращает его в чат с подсказкой, API отвечает 403.
  Ссылка «Заявки службы качества» в шапке чата показывается только роли QUALITY.
- «Сменить пользователя» (ссылка в шапке обеих страниц, `/logout`): браузер держит
  сохранённые учётные данные Basic до закрытия; ответ 401 заставляет его забыть их
  и спросить заново — так в одном браузере меняют роль. Запрос уходит в фоне, со
  страницы никуда не уносит: после ввода учётных данных страница перезагружается
  уже под новой учётной записью, а «Отмена» ничего не меняет.
- Пример вызова API из консоли: `curl -u employee:пароль http://localhost:8090/api/kb`.
- Скриптам `tools/*.py` учётные данные передаются переменными окружения
  `RAG_USERNAME` и `RAG_PASSWORD`, адрес приложения — `RAG_BASE_URL`
  (по умолчанию `http://localhost:8090`); в Bruno учётные данные заданы
  в окружении Local.

Ограничения Basic: пароль передаётся в base64 без шифрования (для localhost
приемлемо, для сети нужен HTTPS); защиты от перебора нет.

## Уточняющие вопросы и уведомления

Если ответ зависит от того, чего нет в вопросе (сумма платежа, тип договора, этап работы),
или вопрос нельзя однозначно отнести к одному месту регламента, агент не выбирает вариант
за пользователя: он задаёт уточняющий вопрос с вариантами ответа, а исходный вопрос
отвечает после ответа пользователя. Подряд задаётся не более
`app.rag.clarification.max-rounds` (3) уточняющих вопросов. Если однозначный ответ всё равно
не получается, агент сообщает об этом и создаёт заявку в службу качества, приложив
уточняющий диалог.

Ответ службы качества приходит в уведомления: значок 🔔 в шапке чата показывает число
непрочитанных ответов на заявки этого диалога, а кнопка «Спросить снова» задаёт вопрос
заново — теперь агент отвечает сам.

## Заявки в службу качества

Вопрос, на который агент не нашёл ответа в регламентах, не остаётся без последействия:

1. Агент создаёт заявку. В таблице `quality_requests` хранится причина:
   `no_context` — не нашлось похожих фрагментов, `not_in_documents` — ответа во
   фрагментах нет, `unverified` — ответ модели не подтверждён дословными цитатами,
   `ambiguous` — агент уточнял вопрос, но однозначного ответа дать не удалось
   (в заявке сохранён уточняющий диалог).
2. Пользователь получает ответ: «ответ не найден, создана заявка №N, обратитесь в службу качества».
3. Служба качества открывает `/quality.html` под своей учётной записью, видит
   список открытых заявок, открывает заявку и пишет ответ.
4. Вопрос вместе с ответом сохраняются в той базе знаний, где вопрос задали, документом
   `Ответ_службы_качества_N<номер>.txt` (тип «ответ службы качества») — с нарезкой и
   эмбеддингами, как у загруженного файла. Дальше агент отвечает на этот вопрос сам
   и ссылается на этот документ.

То же самое из командной строки (нужна учётная запись службы качества):

```bat
set RAG_USERNAME=quality
set RAG_PASSWORD=пароль
python tools\quality_requests.py list
python tools\quality_requests.py answer 12 answer.txt
```

## Запуск в Docker

Та же инструкция отдельным файлом: [DOCKER.md](DOCKER.md).

Приложение и PostgreSQL 17 с расширением pgvector поднимаются одной командой.
Нужен только Docker с плагином Compose (в Docker Desktop он есть, команда
пишется через пробел: `docker compose`); JDK, Maven и локальный PostgreSQL
не требуются.

### Быстрый старт

1. Запустите Docker Desktop. Проверка: `docker compose version` выводит версию.

2. В корне репозитория, рядом с `docker-compose.yml`, должен лежать файл `.env`
   минимум с тремя строками (без кавычек):

   ```dotenv
   AI_API_KEY=...
   APP_AUTH_PASSWORD=...
   APP_QUALITY_PASSWORD=...
   ```

3. Запустите из корня репозитория:

   ```bat
   docker compose up --build
   ```

4. Дождитесь в журнале строки `Started RagAgentApplication` и откройте
   http://localhost:8090/ — браузер спросит логин и пароль.

Первый запуск дольше остальных: скачиваются образы, а образ приложения
собирается Maven’ом (он качает зависимости). Сначала поднимается база и проходит
проверку готовности (`healthcheck`), только затем стартует приложение.
Остановить — `Ctrl+C`.

| Сервис | Образ | Адрес |
|---|---|---|
| `app` | собирается из `Dockerfile` (сборка на Maven + JDK 21, запуск на JRE 21) | http://localhost:8090/ |
| `db` | `pgvector/pgvector:pg17` | `localhost:5433`, база `rag_docs` — только с этой машины |

### Как это устроено

- База создаётся при первом запуске на пустом томе `pg-rag-data`; расширение
  `vector` включает скрипт `docker/postgres/init/01-pgvector.sql` — один раз,
  при создании тома. Таблицы приложение создаёт само при каждом старте.
  Новая база пуста: документы загружаются через страницу чата.
- Данные хранятся в томе: `docker compose down` их сохраняет,
  `docker compose down -v` удаляет вместе со всеми базами знаний.
- По умолчанию порты `8090` и `5433` совпадают с локальной установкой.
  Перед запуском остановите локальное приложение и службу `pg-rag`
  (`net stop pg-rag`) — либо задайте другие порты в `.env` (`APP_PORT`, `DB_PORT`).
- Compose берёт имя проекта из имени папки. Папка раньше называлась `rag-agent`,
  и в Docker могли остаться контейнеры и том того проекта с базой знаний. Чтобы
  пользоваться ими, задайте в `.env` строку `COMPOSE_PROJECT_NAME=rag-agent` —
  иначе создастся второй проект с пустой базой и не сможет занять порт базы.
- Приложение не стартует без ключа и без любого из двух паролей; контейнер `app`
  тогда перезапускается снова и снова, а причина видна в журнале:
  `docker compose logs app`.

### Ежедневные команды

```bat
docker compose up -d --build     :: запустить в фоне; она же пересобирает образ после изменения кода
docker compose ps                :: состояние контейнеров
docker compose logs -f app       :: журнал приложения (выйти — Ctrl+C)
docker compose stop              :: остановить; контейнеры и данные остаются
docker compose start             :: запустить остановленное снова
docker compose down              :: остановить и убрать контейнеры; база остаётся в томе
docker compose down -v           :: то же вместе с томом базы — все документы удаляются
```

После изменения `.env` выполните `docker compose up -d`: контейнеры пересоздадутся
с новыми значениями.

### Переменные `.env`

Значения задаются в файле `.env` рядом с `docker-compose.yml`
(обязательны `AI_API_KEY`, `APP_AUTH_PASSWORD` и `APP_QUALITY_PASSWORD`,
остальные необязательны):

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `APP_PORT` | `8090` | порт приложения на машине |
| `DB_PORT` | `5433` | порт базы на машине |
| `DB_NAME` / `DB_USER` / `DB_PASSWORD` | `rag_docs` / `postgres` / `postgres` | база и учётная запись; приложение получает их автоматически |
| `AI_API_KEY` | — | токен OpenAI-совместимого API (чат и эмбеддинги); без него приложение не запускается |
| `AI_EMBEDDING_API_KEY` | пусто | отдельный ключ для эмбеддингов, если провайдер выдаёт его отдельно от общего |
| `APP_AUTH_USERNAME` | `employee` | логин Basic-аутентификации API и демо-страницы |
| `APP_AUTH_PASSWORD` | — | пароль Basic-аутентификации; без него приложение не запускается |
| `APP_QUALITY_USERNAME` | `quality` | логин службы качества (роль QUALITY — страница заявок) |
| `APP_QUALITY_PASSWORD` | — | пароль службы качества; без него приложение не запускается |
| `QUALITY_SERVICE_CONTACT` | пусто | контакт службы качества для ответа «обратитесь …» |

Например, чтобы Docker-вариант работал рядом с локальной установкой:

```dotenv
APP_PORT=8091
DB_PORT=5434
```

`DB_NAME`, `DB_USER` и `DB_PASSWORD` применяются только при создании базы.
Чтобы изменить их для существующей базы, выполните `docker compose down -v`
(данные базы будут удалены).

### Если что-то не запускается

| Симптом | Что делать |
|---|---|
| `failed to connect to the Docker API` | Docker Desktop не запущен — запустите его и повторите команду |
| Ошибка про занятый порт (`port is already allocated`) | Порт занят локальной установкой: остановите локальное приложение и службу `pg-rag` (`net stop pg-rag`) или задайте другие `APP_PORT` / `DB_PORT` в `.env` |
| Порт базы занят, а локальная установка остановлена; в `docker ps` есть контейнеры `rag-agent-db-1`, `rag-agent-app-1` | Прежняя копия стека под старым именем проекта: добавьте в `.env` строку `COMPOSE_PROJECT_NAME=rag-agent` и повторите запуск |
| Контейнер `app` перезапускается снова и снова | В `.env` нет ключа или одного из паролей — смотрите `docker compose logs app` |
| Страница не открывается, хотя контейнеры работают | Приложение ещё стартует — ждите `Started RagAgentApplication` в журнале; если порт меняли, открывайте `http://localhost:<APP_PORT>/` |

### Перенос данных из локальной базы

База в контейнере изначально пуста. Чтобы перенести в неё базы знаний из
службы `pg-rag` (командная строка Windows, из корня репозитория):

```bat
set PGPASSWORD=postgres
"%ProgramFiles%\PostgreSQL\17\bin\pg_dump.exe" -h localhost -p 5433 -U postgres -Fc -f "%TEMP%\rag_docs.dump" rag_docs
net stop pg-rag                   :: только если DB_PORT=5433 (по умолчанию): порт занят этой службой
docker compose up -d db
docker compose cp "%TEMP%\rag_docs.dump" db:/tmp/rag_docs.dump
docker compose exec -T db pg_restore -U postgres -d rag_docs --clean --if-exists --no-owner /tmp/rag_docs.dump
docker compose up -d --build app
```

## Деплой на Dockhost

`dockhost.yaml` описывает тот же стек для платформы [Dockhost](https://docs.dockhost.ru/manual):
базу `pgvector/pgvector:pg17` на сетевом диске и приложение, которое платформа собирает из
Git-репозитория после каждого push и публикует на домене `*.ds.dockhost.io` по HTTPS.
Нужны [консольная утилита Dockhost](https://docs.dockhost.ru/cli/install) и проект на платформе.

Платформа собирает из репозитория GitHub `https://github.com/XieGAMES/ragprototype.git`
(приватный). В нём лежит весь родительский репозиторий, приложение — в каталоге `rag-agent/`,
поэтому изменения заливаются из корня родительского репозитория:

```bat
git remote add github https://github.com/XieGAMES/ragprototype.git     :: один раз
git add rag-agent
git commit -m "rag-agent: ..."
git push github main
```

### Этап 1 — база, репозиторий, домен

```bat
cd rag-agent
dockhost project use <проект>
dockhost compose apply
```

Будут созданы переменная проекта `DB_PASSWORD` (пароль генерируется и выводится командой,
список переменных — `dockhost environment variable list`), диск `pgdata`, база `db`,
репозиторий `app` и домен; платформа начнёт первую сборку. Репозиторий приватный, а утилита
не передаёт логин и пароль из `dockhost.yaml`, поэтому доступ задаётся отдельно — токеном
GitHub с правом чтения репозитория:

```bat
dockhost repository update app --url https://github.com/XieGAMES/ragprototype.git --branch main --username XieGAMES --password <токен>
dockhost repository build app
```

### Этап 2 — приложение и маршрут

Когда сборка пройдёт, создайте секреты проекта (в файле их нет) и посмотрите имя образа,
которое платформа присвоила контейнеру `app`:

```bat
dockhost environment variable set --name AI_API_KEY --value <ключ>
dockhost environment variable set --name AI_EMBEDDING_API_KEY --value <ключ>
dockhost environment variable set --name APP_AUTH_PASSWORD --value <пароль входа>
dockhost environment variable set --name APP_QUALITY_PASSWORD --value <пароль службы качества>
dockhost compose dump --file project.yaml
```

Затем впишите это имя (`containers` → `app` → `image` в `project.yaml`) в `containers.app.image`
файла `dockhost.yaml`, уберите `#` у блоков с пометкой «Этап 2» и примените файл ещё раз:

```bat
dockhost compose apply
```

- Адрес приложения — домен, созданный на этапе 1; вход — `APP_AUTH_USERNAME` / `APP_AUTH_PASSWORD`.
- База наружу не опубликована. Подключение с машины: `dockhost network port-forward --project <проект> db 5435:5432`,
  затем `psql -h localhost -p 5435 -U postgres rag_docs` (пароль — `DB_PASSWORD`).
- `dockhost compose delete` удаляет всё описанное в файле, включая диск с базой знаний.

## API

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/ask` | `{"question": "..."}` → ответ, источники и дословные цитаты (`found`, `quotes`); если ответа в регламентах нет — `found=false`, `escalated=true` и номер созданной заявки `requestId` |
| POST | `/api/documents` | multipart: `file`, `docType`, `title` — загрузка в базу знаний |
| GET | `/api/documents` | каталог загруженных документов |
| DELETE | `/api/documents?file=...` | удалить документ из базы знаний |
| GET | `/api/quality-requests?openOnly=true` | заявки службы качества (роль QUALITY) |
| POST | `/api/quality-requests/{id}/answer` | `{"answer": "..."}` — ответ службы; вопрос и ответ сохраняются в базе знаний документом |
| DELETE | `/api/quality-requests/{id}` | удалить заявку |

Все эндпоинты требуют Basic-аутентификацию — см. раздел «Аутентификация».

## Как проверить (сценарий демо)

1. Загрузить 3–4 документа: регламент договорной работы, приказ о матрице
   ответственности, инструкция по командировкам, шаблон агентского договора.
2. Спросить: «Кто подписывает агентский договор?» → ответ со ссылкой
   на пункт регламента, процентом сходства и дословными цитатами.
3. Спросить что-то, чего в регламентах нет → агент не выдумывает: отвечает,
   что ответа нет, и создаёт заявку в службу качества.
4. Открыть `/quality.html` под учётной записью службы качества → заявка в списке;
   ответить на неё → вопрос и ответ сохранились документом в базе знаний.
5. Снова спросить тот же вопрос под учётной записью пользователя → агент
   отвечает сам, ссылаясь на ответ службы качества.
4. Загрузить обновлённую версию регламента под тем же именем → старая
   версия заменяется, агент отвечает по актуальной.

## Настройки

`src/main/resources/application.yml`: модель чата и эмбеддингов, размеры
`top-k` / порога сходства (`app.rag.*`), строка подключения к БД.

Адрес API и модели — в `application.yml` (`spring.ai.openai.*`). `base-url`
указывается без `/v1`: Spring AI сам добавляет `/v1/chat/completions` и
`/v1/embeddings`.

При смене модели эмбеддингов ничего не перезагружать вручную не нужно. При
первом обращении к каждой базе знаний приложение сверяет модель, которой
получены её векторы, с текущей и при расхождении заново считает эмбеддинги
по сохранённому тексту чанков (`EmbeddingReindexer`) — исходные файлы не
нужны. Первый запрос по базе после смены модели поэтому дольше обычного.
Размерность векторов определяется по ответу API.

Строгость ответа: `app.rag.answer.max-attempts` — сколько раз агент переспрашивает
модель, если её ответ не подтверждён дословными цитатами; после этого создаётся
заявка в службу качества. `app.rag.quality.contact` — контакт службы качества
в ответе «обратитесь …» (пусто — без контакта).

Порог сходства `app.rag.similarity-threshold` (`0.35`) подбирался под прежние
модели эмбеддингов: если ответы тянут лишние источники или теряют нужные,
его стоит пересмотреть.
